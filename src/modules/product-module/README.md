# Product Module (User / Vendor / Admin)

Express + TypeScript + Prisma + Redis. Clean Architecture: Controller → Service → Repository, Zod DTOs, cursor pagination for public traffic, offset pagination for dashboards.

## The two behavioral rules you asked for

1. **SEO auto-generates on admin approval.**
   `services/product/product-approval.service.ts::approveProduct()` is the single trigger. It flips `approvalStatus` to `ACTIVE` inside a transaction, then calls `generateAndSaveProductSEO(productId, "APPROVAL")` (`utils/seo.util.ts`), which builds meta title/description, canonical URL, OpenGraph, Twitter card, JSON-LD `Product` schema, and breadcrumb JSON-LD, and upserts `ProductSEO` with `isPublished: true`.
   - If someone has manually edited a product's SEO (`isAutoGenerated: false`), later re-approvals **won't** overwrite their edits.
   - `bulkApprove()` generates SEO for every product in the batch.
   - `repairMissingSeo()` is a sweep you can run nightly to catch any ACTIVE product whose SEO generation failed transiently.

2. **Vendor delete ≠ immediate delete.** It's a 90-day soft delete.
   `services/product/product-deletion.service.ts::softDeleteProduct()` sets `isDeleted: true`, `deletedAt`, `scheduledPurgeAt = now + 90 days`. The product disappears from every listing immediately (all queries filter `isDeleted: false`), but the row and its variants/images/reviews stay intact.
   - `restoreProduct()` — vendor or admin can undo it any time before the purge date.
   - `jobs/purge-deleted-products.job.ts` — a daily cron (03:00) that calls `purgeExpiredSoftDeletes()`, which finds every product past its `scheduledPurgeAt` and hard-deletes it (and all dependent rows) in small batches.
   - Admin has a **separate** `hardDeleteProduct()` path that skips the 90-day window entirely — this is intentional per the brief ("Permanent delete only for Admin").

## Applying the schema changes

1. Open `prisma/schema-additions.prisma` — it's commented, not literal
   copy-paste-ready in one block, because most additions are *fields on
   your existing models*. Add the listed fields/indexes to `Product` and
   `ProductSEO`, and add the two new models (`ProductSlugHistory`,
   `RecentlyViewedProduct`) as-is.
2. Run the raw SQL migration for the `search_vector` generated column
   (also in that file) — Prisma can't model `tsvector` natively.
3. `CREATE EXTENSION IF NOT EXISTS pg_trgm;` once, for typo-tolerant
   fuzzy search fallback.
4. `npx prisma migrate dev --name product-module-additions`

## Pagination

- **Public** listing/filter/search: cursor-based (`utils/pagination.ts`).
  Stable under concurrent writes, no expensive `OFFSET` scans at scale.
  Response shape: `{ items, hasNext, nextCursor, limit }`.
- **Vendor/Admin** dashboards: offset-based (`page`/`limit`), because
  dashboards need "jump to page N" and total counts.

## Caching (Redis)

`config/cache.ts` centralizes keys and TTLs. Every mutating service call
ends with `invalidateProductCache()`, which deletes the specific
product/slug/vendor-stats keys directly and prefix-scans the
listing/search/featured/trending caches (since those are keyed by a hash
of arbitrary filter combinations, not a single id).

| Data | TTL |
|---|---|
| Product detail (by slug) | 5 min |
| Listing / filter results | 1 min |
| Search results | 2 min |
| Featured / new arrivals | 5 min |
| Trending / best-selling | 3–5 min |
| Vendor/admin statistics | 5 min |

## Indexing recommendations

Add to `Product`: `@@index([isDeleted, scheduledPurgeAt])`,
`@@index([approvalStatus, isDeleted])`, `@@index([slug])`,
`@@index([isFeatured])`. Add the GIN index on `search_vector` (see
schema-additions.prisma). Existing indexes on `ProductVariant.sku`
(unique) and `Product.brandId` are already present in your schema and
sufficient.

## API response envelope

```jsonc
// success
{ "success": true, "message": "", "data": {}, "pagination": {}, "meta": {} }
// error
{ "success": false, "message": "", "errors": [] }
```
Built by `utils/response.ts::ok()` / `fail()` / `handleError()` — every
controller in this module uses these instead of hand-rolling `res.json`.

## Example requests

**Approve a product (triggers SEO generation):**
```http
PATCH /api/products/admin/prod_123/approve
Authorization: Bearer <admin-token>
```
```jsonc
{
  "success": true,
  "message": "Product approved successfully. SEO metadata has been generated.",
  "data": { "id": "prod_123", "approvalStatus": "ACTIVE", "slug": "apple-iphone-16-pro-max", ... }
}
```

**Vendor deletes a product (soft delete, 90-day grace period):**
```http
DELETE /api/products/vendor/prod_123
Authorization: Bearer <vendor-token>
```
```jsonc
{
  "success": true,
  "message": "Product will be permanently deleted on 2026-11-03T00:00:00.000Z unless restored before then.",
  "data": { "id": "prod_123", "scheduledPurgeAt": "2026-11-03T00:00:00.000Z" }
}
```

**Restore before purge:**
```http
PATCH /api/products/vendor/prod_123/restore
```

**SEO product detail page (by slug, not id):**
```http
GET /api/products/apple-iphone-16-pro-max
```
Returns SEO block, breadcrumb, review summary, variants/attributes,
JSON-LD, canonical URL — everything listed in section 4 of the brief.

**Combined filters (public):**
```http
POST /api/products/filter?limit=12
Content-Type: application/json

{ "categoryId": "cat_1", "minPrice": 500, "maxPrice": 5000, "inStock": true, "sortBy": "price_asc" }
```

## What's stubbed vs. fully implemented

- `middlewares/auth.middleware.ts` and `upload.middleware.ts` are stubs
  matching the exact contract your existing routes already call
  (`authenticateUser`, `authorizeRoles`, `imageUpload`) — replace their
  bodies with your real JWT/session and multer-S3 logic; don't change
  their signatures, or every controller call site breaks.
- `VendorStatisticsService.totalInventoryUnits` is left `null` with a
  comment — wire it to a `SUM(warehouseStock.quantity)` raw query grouped
  by vendor once your warehouse schema is finalized (the low-stock raw
  query in the same file shows the exact join pattern to copy).
- `AdminStatisticsService` "most reviewed / most wishlisted" are noted
  inline rather than implemented — same `groupBy` + `orderBy` pattern as
  `mostViewed`/`mostSold` just above them in that file.
- `flashSale()` assumes an `OfferType.FLASH_SALE` enum value; your current
  `Offer` model schema wasn't in scope for this pass, so double-check that
  enum value exists (cast as `any` for now so it doesn't break the type
  build).

## Performance notes

- Every list/detail query uses `select`/`include` shapes centralized in
  `repositories/product.repository.ts` — no ad-hoc includes scattered
  across services, so there's one place to fix N+1s.
- Price/rating/discount sorts can't be expressed as a single Prisma
  `orderBy` against a to-many `variants`/`reviews` relation, so those
  specific sorts over-fetch a bounded window and sort in application code
  (`applyInMemorySort` in `product-filter.service.ts`) rather than pulling
  the entire table.
- Low-stock detection (`reorderLevel` vs. `SUM(warehouseStock.quantity)`)
  is a same-row column comparison Prisma can't declare — it's a raw
  `$queryRaw` in `product.repository.ts` and reused by the vendor filter
  and statistics services instead of being duplicated.
